# Carrier and system

Read this module when the carrier, content relationship, color climate, component language, or visual direction is unresolved.

## Fast paths

- Stable reading, form, table, disclosure, and ordinary controls default to semantic DOM; bounded topology defaults to SVG when that relationship is already clear. Record the reason inline without loading the rendering-medium reference.
- Load [rendering-medium.md](rendering-medium.md) for every decisive screen. Skip it only after recording which medium-risk predicate is false and why; time, depth, continuity, procedure, many marks, or direct manipulation each make it mandatory, as does any screen with two plausible media. `The stack is React`, `DOM is faster to build`, and `the relationship looks simple` are not predicates.
- Equivalent prose or disclosure sections may share one section-model contract. Model each section separately only when its entities, relationships, protected state, or semantic invariant differs.

These predicates scope the preserved requirements below; once triggered, none of their carrier, system, separation, or spatial safeguards may be skipped.

Carrier and rendering medium are separate decisions. The carrier names what bears the evidence; the medium names how a particular screen renders and behaves. `Graphic` does not imply DOM/CSS, and `WebGL` or `Three.js` does not supply a content model or communication purpose. Do not let the current framework, team familiarity, or the fastest first implementation select the medium by default.

**REQUIRED when an approved source has not already protected the technique:** read [references/rendering-medium.md](references/rendering-medium.md) before visual composition. Run its medium scan for each decisive screen, choose from the plausible set rather than imposing one renderer page-wide, and keep copy, navigation, controls, semantics, and the meaningful fallback in accessible DOM. When depth, continuous transformation, procedural material, spatial continuity, particles, or direct manipulation could materially improve the evidence, the plausible set must include at least one non-DOM candidate. Advanced rendering is never a quota: a reading, policy, table, form, or disclosure screen should deliberately reject it when it adds no meaning.

Before choosing a macro layout, classify every section by the facts it must make visible. This is unconditional, including sections that initially look like ordinary copy or reusable cards. The skill owns the first recommendation; do not make the user invent an organization chart, flow, or diagram unless the factual relationship itself is ambiguous.

| Evidence in the content | Content model | Starting visual grammar |
|---|---|---|
| Ordered steps, time, or lifecycle | Sequence | Ordered path or timeline with explicit state changes |
| Input becomes a different retained result | Transformation | Before → boundary → after, with discarded and retained states separated |
| Multiple routes share one rule | Branch + invariant | Branches joined at their nearest common condition or parent |
| A request must satisfy permissions or policy | Gate | Request → named gates → allowed or blocked endpoint |
| Location, ownership, or protection encloses another fact | Containment | Nested boundaries with the protected item inside its actual owner or region |
| Authority or responsibility descends through levels | Hierarchy | Tree, tiers, or nested responsibility field |
| Like-for-like alternatives must be judged | Comparison | Aligned matrix or shared-axis comparison |
| Independent peer evidence has no causal relationship | Inventory | Ledger, table, or list |
| One proposition is proved by a moment or artifact | Narrative | Focused photo or product state with adjacent proof |

These are semantic starting points, not templates. Combine models when the claim combines them: `organization policy → allowed route → Seoul region → encrypted storage → protected record` requires a gate plus nested containment, not three peer cards. A polished inventory is a failure when the facts are not peers.

Motion is behavior applied to the carrier when time or state change is essential; it is not a second art direction. Define start, end, trigger, stoppable states, reduced-motion state, and what the motion explains.

When the carrier uses or could plausibly use an asset, record its plan before composition:

When multiple routes inherit the same verified constraint, show the route-specific input and purpose at each branch, then state the invariant once at their nearest common parent. Repeating the same retention, privacy, or policy condition inside every branch falsely suggests separate rules and weakens the conclusion. The common constraint must read as the result of the branches, not as another peer route.

The carrier fails when it shows architecture but not the promised constraint, or when a vendor, destination, or decorative object is more prominent than the relationship on which the claim depends. Fix hierarchy or choose another carrier; copy presence is not visual proof.

A new page-wide concept may change surface, typography, density, or motion, but it cannot silently replace a section's content model. Before replacing an earlier evidence-bearing carrier, compare `visible entities / visible relationships / protected or changed state / label-hidden inference`. Preserve the earlier relationship model unless the new carrier explains the same facts at least as clearly. This is a semantic benchmark, not a requirement to copy the old styling or exact geometry.

A person or environment may humanize trust only when the image is credible and specific to the product context. A shield, futuristic gradient, network pattern, or dark field is not security evidence by itself. Use a category convention only when it improves comprehension or carries verified meaning.

Treat cliché avoidance as a quality constraint on asset selection, not permission to omit photographic or graphic exploration. When photo or graphic could carry the evidence more directly than copy and cards, compare that carrier in the decisive scene before choosing a layout-only solution. For a generated or edited asset, lead the production brief with communication purpose, evidence, subject, and transformation; material and style terms come after those decisions. Review the raw asset and complete composition separately.

Resolve exact color and material values in this order:

1. active project design-system tokens and components;
2. current Tiro web or product surfaces;
3. the relevant Tiro skill or maintained brand source;
4. external references, for role and distribution rather than unapproved exact values.

Name the inspected path or URL. When sources conflict, surface the conflict instead of averaging them. Do not load every Tiro skill by default; inspect only the source relevant to the active decision.

Treat design-system conformance as an implementation gate, not a mood reference. Before composing the page, map each used role to its governing source:

```text
Role: typography / color / spacing / radius / elevation / icon / action / state
Governing token or component:
Landing alias or composition use:
Applicable states and breakpoints:
Gap or conflict:
Approved exception and owner:
```

Do not create a near-match hex, font size, radius, shadow, button treatment, or hover/focus/pressed behavior when an active Tiro token or component role exists. Landing composition may change scale, placement, density, and surface distribution, but it must consume or alias the verified system rather than restyling the primitive locally. When the product system has no public-page role, derive one from the maintained site-family contract, name it as a local semantic alias, and record the gap; do not silently invent a value. A candidate cannot enter visual composition or release review while any visible control or repeated style has an unmapped role.

Enforce the map in implementation, not only in the brief:

- Reuse a maintained Tiro component when it already owns the required semantics and states. If landing-specific composition needs a wrapper, keep the primitive unchanged and style the wrapper by role.
- Reference the active token or a named semantic alias in source. Do not paste the token's current literal value into page-local CSS.
- Verify typography by role and computed size, not by visual resemblance. A display face, body face, weight, line height, or breakpoint scale that is not mapped fails even when it looks close.
- Verify every visible action in `default / hover / focus-visible / active or pressed / disabled when applicable / loading when applicable`. A missing state is a design-system gap to resolve, not permission to improvise one on the page.
- Treat buttons, links styled as buttons, chips, disclosure triggers, local navigation, and form controls as one action inventory. Their color, border, radius, icon spacing, target size, and state changes must trace to the same governing system.
- Add a source-level conformance check for repeated primitives when the project has automated tests. Before release, inspect at least one primary and one secondary action in the browser and record their computed typography, foreground, background, border, radius, and state behavior.

Site-family continuity does not require every chapter to inherit the same dominant hue or warm-versus-cool distribution. When a chapter has a distinct belief or after-feeling, re-map the approved palette by area: broad fields may become neutral, stone, graphite, or near-black while brand continuity remains in typography, logo, product evidence, or restrained accents. Use exact values only from an approved source; keep an unsupported direction semantic until the source is established.

Use solid for the primary conversion action, outline for supporting actions, and ghost or text for low-priority navigation unless the active system defines otherwise. A gradient outline is an expressive exception with a communication job, not a default secondary style. Derive radii from the active system and the page geometry. Reserve pill treatment for short actions, chips, or a deliberately pill-led family; do not round every button, card, chip, and product panel equally.

### Keep hover feedback in plane

On landing pages, mouse hover **must not move the outer box of a component**. Do not use `translate`, scale-up, tilt, bounce, spring, or a stronger shadow to make a card, button, CTA, row, image, or diagram panel appear to float. This prohibition still applies when a shared utility already exists, a deadline makes reuse convenient, a stakeholder asks for more “delight,” or consistency is offered as the reason. Repeating a weak effect is not system consistency.

Default hover feedback stays in plane: change a verified foreground, background, border, underline, opacity, or an internal arrow/icon while the component bounds and surrounding reading rhythm remain fixed. Keep `:focus-visible` at least as clear as hover, never put meaning in hover alone, and give `:active` or `:pressed` its own intentional response instead of reusing simulated elevation.

| Shortcut | Decision |
|---|---|
| “The shared utility already lifts everything.” | Do not reuse it on the landing surface; system consistency does not preserve a rejected effect. |
| “The review is soon, so lift is the fastest polish.” | Ship restrained in-plane feedback or no hover polish; urgency does not create a semantic job. |
| “The page needs delight or more interactivity.” | Express it through the carrier, state, or internal affordance; moving every clickable box is not art direction. |

If the landing page embeds a verified product interaction in which literal spatial movement is the behavior being demonstrated, preserve that movement inside the product frame. This exception does not authorize lift hover on the surrounding landing-page chrome, cards, or actions.

Assign one job to every separation mechanism. Resolve section separation in this order: content grouping and proximity; composition, carrier, density, and silhouette; whitespace rhythm; a meaningful surface change; then a line for an exact boundary. A divider may enter earlier only when a visible grid, ledger, table, timeline, or named boundary is the page mechanism. A divider between peer rows is not permission to divide unrelated page chapters. If removing a line loses no relationship, remove it.

Use whitespace when the argument continues without a new surface, a quiet background for mood or semantic grouping, an accent background only for real emphasis, a border for an exact boundary, a shadow only for a raised artifact, and a gradient only for a field transition or connection. Site-structure lines and product-interior lines are separate roles even when they share a hue. State whether each line crosses the viewport, follows the page container, connects into adjacent boundaries, or ends as an inset divider. For every line, including pseudo-elements, name the exact start element, end element, and relationship it makes easier to read. A metaphor such as `spine`, `trace`, or `flow` is not evidence when the rendered line does not physically bind those elements. Delete a line that begins or ends in empty space, stops short of the relationship it claims to connect, or duplicates grouping already carried by spacing or a surface. Do not stack mechanisms merely to make a section feel designed.

When a landing surface should feel continuous with Tiro's product, inspect a current rendered product surface or maintained product Evidence before styling it. Translate the relationship between background, border, radius, inset, and elevation; do not copy an app panel's literal width or layout. Alias the verified product token instead of recreating a similar-looking local shadow.

- Keep site chrome flat while it shares the page field. Apply the product's sticky depth only after the header overlaps content or opens an overlay.
- Give dropdowns, functional overlays, and embedded product windows the verified raised-surface, border, radius, and floating-elevation relationship.
- Keep marketing stages, section fields, and ordinary content cards flat unless their composition establishes real overlap or height above the page.

The outer decorative shell must not cast more depth than the product object it presents. Several custom blur recipes do not create product continuity; they create unrelated local atmospheres.

Every deliberate departure in type size, weight, color, alignment, offset, line, gradient, shape, or motion must state what meaning would be lost if it were normalized. `It feels more interesting` is not a job. Before approval, run an orphan-element audit: remove any line without a readable start, end, and relationship; any isolated color without a named role and source; any type change without hierarchy or state meaning; and any decoration or stoppable motion state that becomes intelligible only after an effect completes.

For every bounded composition, write this spatial-frame contract before choosing DOM, grid, or styling:

```text
Bounds owner: page / section / carrier / component
Coordinate frame: the exact outer box that top / bottom / left / right refer to
Occupied anchors: major item → corner / edge / center / shared axis
Intentional empty regions:
Reading path:
Optical corrections after structural alignment:
Breakpoint reassembly and preserved semantic order:
```

Directional instructions such as `top-left` are incomplete until the coordinate frame is named. Keep that frame stable from brief through implementation: an outer-composition corner cannot silently become the corner of an existing column, nested cell, or prior component slot. Treat the current grid as implementation evidence, not the bounds owner. When the user supplies a drawn or described virtual boundary, transcribe that boundary and its empty regions before adapting the existing layout. If the frame remains genuinely ambiguous, show an annotated skeleton or state the frame assumption before polishing.

Verify both structural and optical alignment. If the reading path is corner-based, name the sequence and make adjacent anchors close the shape; local centering may not relocate a logo, icon, or action between semantic cells. At each breakpoint, confirm that no item protrudes from the named box and that reassembly preserves the reading order.

If this language is unresolved, compare one actual-size calibration strip on the real page backgrounds: primary, secondary, text action, chip, product panel, card, and focus state. Do not build several full pages to decide button styling.

Approve the reference premise, primary carrier, screen-specific rendering-medium map, and component language together before visual composition.

Do not browse React component or rendering-library catalogs while these decisions remain unresolved. A focused specialist feasibility query is allowed only through the routing contract when the medium scan has narrowed the question but cannot settle it. After approval, a library search may answer only a bounded implementation question for the chosen carrier, medium, and behavior. Inspect the current package and component stack first, then choose one existing primitive or one library; do not assemble a page around an attractive catalog component. Use the specialist routing reference for Componentry, Skiper UI, Watermelon, Cult UI, shader helpers, WebGL or Three.js specialists, and UI Skills library-selection guidance.
