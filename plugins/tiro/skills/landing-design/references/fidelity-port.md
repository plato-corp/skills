# Fidelity port

Read this module only through the exclusive `fidelity-port` route. Activate it when a distinct approved rendered source is being translated, moved, ported, integrated, migrated, converted, or deployed into a destination. An approved page receiving an in-place correction stays on the bounded `polish`, `craft`, or `release` route. This module outranks job-specific strategy and visual preferences inside the source-owned boundary.

This route already owns source-translation and responsive-parity risk. Do not layer job modules or ordinary risk modules on top; doing so would silently reopen protected decisions. Add specialist guidance only for one concrete gap that this route cannot resolve.

Visual-completion and implementation checks diagnose translation or integration drift only. They must not reopen approved copy, hierarchy, component geometry, hover behavior, color, medium, or responsive composition. Apply global landing rules to destination-owned shared chrome and infrastructure; preserve conflicting source-owned behavior unless the user names it as an explicit delta.

### Fidelity-port mode for an approved source

Select `fidelity-port` when the user identifies an existing rendered implementation as approved, final, preferred, or the source to move, integrate, migrate, convert, or deploy. This is an integration task, not a new direction. Inside the page-content boundary, the approved source outranks the destination repository's sibling-page defaults, generic landing conventions, and any agent preference for a more coherent or polished result.

Complete this entry gate **before the first production edit**:

```text
Canonical source: exact path or URL, revision when known, and rendered capture provenance
Destination: repository and routes
Boundary: source-owned page content / destination-owned shared chrome and infrastructure
Protected decisions: exact copy and phrase breaks / section order / macro layout / color roles and area distribution / fonts and computed type scale / containers and spacing rhythm / surfaces, borders, radii, and shadows / assets / rendering medium and layer ownership / responsive breakpoints and reassembly / interaction behavior
Explicit deltas: only changes the user requested
Translation method: preserved namespaced source or one-to-one framework mapping
Pre-edit checks: source-level assertions or rendered baselines that fail on protected drift
Unresolved destination conflict:
```

No production edit begins while the canonical source cannot be rendered, the boundary is unnamed, the protected-decision ledger is incomplete, or the destination requires a visible change outside an explicit delta. Capture and assertions are not merely release checks: establish them against the source first so the implementation starts inside the approved contract.

The first implementation is mechanical. Prefer preserving and namespacing the source markup and stylesheet. When framework semantics require different markup, map every source-owned rule one-to-one before extracting components or consolidating styles. Framework syntax, component boundaries, asset paths, routing, accessibility semantics, and shared Header or Footer may change only when the rendered page-content result and behavior remain equivalent.

Do not restart `shape`, `direction`, `carrier`, color-climate selection, site-family normalization, or design-system reinterpretation for protected content. Do not substitute “same feel,” “adapted to the host,” or “cleaner in React” for equivalence. An explicit user-requested delta unlocks only the named property or region; every other protected decision stays frozen. Autonomous mode means continue without repeated approval while honoring this ledger. It never unlocks redesign.
